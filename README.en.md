# HyprBuddy OS

**A reproducible, auditable, rollback-safe agent desktop.**

HyprBuddy OS is a NixOS flake that turns "what an agent is allowed to do on this machine" into a **buildable, queryable, revertible artifact**. The desktop shell is the carrier, not the point: niri 26.04 + Noctalia v5 run on top, but the project is defined by declarative configuration, a machine-readable capability manifest, and explicit permission boundaries.

This is **not** an "AI-native desktop". There is no screenshot timeline, no Recall-style memory, no background assistant watching you, and no **built-in inference that requires the network** (agent orchestration may still call external LLM APIs). Local inference (ollama) is **off by default** and, when enabled, binds to `127.0.0.1` by default.

## Why

Three common failure modes when agents become part of a desktop, and the answers implemented here:

| Problem | Usual approach | HyprBuddy OS |
|---|---|---|
| Config is a pile of dotfiles; reproducing it on another machine means copy-paste | install scripts + tutorial | `flake.nix` / `flake.lock` + git; each host writes only `distro.*`; the same flake evaluates to the same system |
| Update channel is locked to a vendor repo; recovery is hard | follow the vendor's upgrades | No private update channel; three revert levels: `nixos-rebuild --rollback`, `git revert`, re-run `install.sh` |
| Agent capabilities are opaque; generated scripts mutate `/etc` or auto-elevate | bind agent CLIs to a hotkey | `@effect` / `@requires-sudo` metadata, read-only by default, **sudo commands printed but never executed**, and a decoy `/etc/nixos/configuration.nix` that fails any imperative rebuild |

## Three principles (implemented, not planned)

### 1. Configuration is an artifact

All system capabilities live in `modules/`, all machine differences in `hosts/<host>/default.nix` as typed `distro.*` options with assertions. Two kinds of writes are strictly separated:

- **User-level** (`home/`, `lib/`, `scripts/`, `skills/`) → `./install.sh --host <host> --yes`, no sudo, verifiable immediately.
- **System-level** (`hosts/`, `modules/`) → the agent edits the repo and builds it; the sudo command is handed to the human.

`/etc/nixos/configuration.nix` is a deliberate **tripwire**: a rebuild without `--flake` reads it and fails, so neither a user nor an agent can silently turn the system imperative.

### 2. Capabilities are machine-readable and build-validated

`lib/gen-commands.py` parses `@command` headers in `scripts/` and emits `commands.json`. These are hard build failures, not conventions:

- `@command`, `@summary`, `@category` are required; `@command` must equal the filename; `@category` is restricted to `runtime / workflow / check / agent / system`.
- `@effect` → `effects[]`; `@requires-sudo` → boolean; `@arg`, `@usage`, `@interactive` describe the interface.
- `@doc` must point to a real guide under `skills/<skill>/`, otherwise **the build fails** (no dead references).

The manifest also carries `generated` (host, version, `agent_enabled`, `scripts_source` build fingerprint), a per-command `available` flag reflecting *this machine's* build, unified `paths` (including `paths.artifacts`), and ops recipes. Query it with:

```bash
agent-commands --json          # source of truth
agent-commands list | show <name> | --category <cat> | paths
```

### 3. Agent permissions have a boundary

`scripts/agent-apply` is the single entry point for agent-driven changes and does exactly four things:

```
git diff --stat  ->  nix eval (toplevel drvPath)  ->  nixos-rebuild build  ->  print sudo command
```

Bad configuration surfaces at **build time**, never in the running system. `sys-*` commands are read-only or print-only. Core-dump reports generated by a local model must be cross-checked against `coredumpctl info`.

## Reproduce

Prerequisites: a NixOS 26.05 machine (or install from this repo's ISO), `nix-command` + `flakes`, `git`, and (on CN networks) access to `mirrors.tuna.tsinghua.edu.cn`. The ISO ships a local nixpkgs source, so installation does not depend on the mirror; overseas or other networks can switch binary caches with `--mirror official`.

```bash
git clone https://gitee.com/lele2015/hyprbuddy-os.git
cd hyprbuddy-os && git checkout distro/v1-nn
cp -r hosts/_template hosts/<your-host>       # edit distro.* for your GPU / hypervisor
./install.sh --host <your-host> --yes          # user-level links
sudo nixos-rebuild boot --flake .#<your-host> # system-level, executed by you
desktop-check                                 # 19 checks; degrades outside a graphical session
agent-commands --json                         # what is actually available on this host
```

Two rules: **the flake only sees git-tracked files** (commit before install/build), and `nixos-rebuild switch` does not deploy user-level config — run `install.sh` separately.

## Agent layer today

- **28 commands**. The `@category` enum allows `runtime / workflow / check / agent / system`; current distribution is `check` 11 (`sys-health`, `svc-status`, `sys-log`, `net-status`, `power-status`, `model-status`, `model-bench`, `sys-gc`, `sys-rollback`, `desktop-check`, `agent-commands`), `runtime` 14 (`theme-next`, `theme-picker`, `de-theme-apply`, `wallpaper-next`, `night-mode`, `notif-dnd`, `sddm-theme`, `clipboard-menu`, `record-toggle`, `screenshot-output`, `screenshot-annotate`, `agent-menu`, `sysinfo-os`, `show-sysinfo`), `workflow` 2 (`agent-apply`, `sys-update`), `agent` 1 (`agent-theme-sync`); `system` is currently unused. This describes the *repository*, not a given host — trust `available` in `commands.json`. `install.sh` is a deployment script, not one of the 28 commands.
- **5 skills** with a routing table and a skill×command matrix (`docs/SKILLS.md`): `nixos-desktop-settings`, `nixos-system-ops`, `theme-create`, `scifi-ui`, `diagnose-crash`.
- **Local models: code ready, switched on for `leonard` only (runtime not yet verified).** `modules/agent/local-llm.nix` defaults to the CPU package (`pkgs.ollama-cpu`, no CUDA/ROCm toolchain in the system closure) and pins `host = "127.0.0.1"`; GPU variants are opt-in via `distro.agent.ollamaAcceleration = "gpu"`. `leonard` has `localModels` + `diagnostics` on in the repo, but the system has not been switched and no model has been pulled, so `ollama.service` and the coredump path are **not verified**. `vmware` / `vm-virtio` keep `localModels = false` (`vmware` also has `agent.enable = false`, so the whole module is inactive). There is no verified OpenAI-compatible endpoint, concurrency control, or power telemetry yet. The endpoint itself is now configurable through `distro.agent.localEndpoint`: `bind` (default `127.0.0.1`), `lan` (default `false`), `maxConcurrent` (default `1`, exported as `OLLAMA_NUM_PARALLEL`), plus three build-time assertions that reject half-open combinations. `token` only writes `~/.config/hyprbuddy-os/local-endpoint.env` for client convenience — **ollama does not validate it**. Listed as a next step in progress, **not** a shipped feature.

Desktop shell details (60 niri keybinds, 10 token-based themes, `desktop-check`, `scripts/lib/de.sh`) are in the Chinese README.

## Non-goals

> This is the **authoritative boundary list**; `docs/ROADMAP.md` §5 refers here. Entries mix three tones: hard red lines, defaults that can be explicitly enabled, and historical scope cleanup. Changes must satisfy the admission rules in `docs/ROADMAP.md` §1.

- **System-level AI features**: continuous screenshot indexing, Recall-style memory, an assistant that acts on the user's behalf unprompted. The audit direction records **agent** execution events only; see `next-feature/agent-execution-audit.md` (not implemented).
- **"AI-native OS" / "Copilot+ parity" branding** and TOPS-driven marketing. Using an NPU does not mean marketing TOPS: the metrics are always-on power draw and concurrency isolation, not TOPS / tok/s comparisons.
- **Built-in inference must not require the network** (this does not forbid agent orchestration calling external LLM APIs). Local models are **off by default** and bind to `127.0.0.1` **by default**. LAN exposure (`distro.agent.localEndpoint`) is off by default and requires an explicit `lan = true` plus a non-loopback `bind`; it is bounded by a concurrency cap (`OLLAMA_NUM_PARALLEL`) and build-time assertions. `token` is a client-side convention only — ollama validates no token, and **real authentication needs a reverse proxy, which this repo does not ship**.
- **Agents executing sudo, editing `/etc` directly, or bypassing build verification**.
- **Private update channels or a config format tied to a single vendor repository**.
- **Chasing UI parity with other distros** (multi-terminal / editor switching, dev stacks, game bundles): no differentiation at that layer; personal needs belong on a personal branch.
- **Wrapping package-manager commands** (declarative config already covers it); **Hyprland / COSMIC features** (retired 2026-10-28).
